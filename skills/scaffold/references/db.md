# Database

`packages/db` (or `src/db` in a single package): migrations generated by the ORM, committed, and applied explicitly. Database credentials exist only in backend apps; Native and Desktop bundles never contain them.

## Local Postgres

- One root `compose.yaml` with a Postgres service, a `pg_isready` healthcheck, and a named volume. Host port `${POSTGRES_PORT:-5432}`, bound to `127.0.0.1`.
- `.env.example` documents `POSTGRES_PORT=5432` and `DATABASE_URL` built from it. `${POSTGRES_PORT}` inside `DATABASE_URL` needs a loader that expands variables (`@next/env` does; plain `dotenv` and `--env-file` do not); otherwise write the literal port and note that both change together.
- Root scripts: `"db:up": "docker compose up -d --wait"`, `"db:down": "docker compose down"` (keeps the volume), plus `db:generate` (writes a migration) and `db:migrate` (applies migrations) delegating to the db package. `--wait` returns once the healthcheck passes, so migrations can follow directly.
- Before the first `db:up`, check that the port is free; if not, set a free `POSTGRES_PORT` in `.env`.
- Leave the Compose project name at its default, the folder name: each worktree then gets its own containers and volume.

AGENTS.md and README state: "Parallel worktree: change `POSTGRES_PORT` in that worktree's `.env`." Add a TODO there: automate per-worktree port assignment if manual ports become painful.

## Local SQLite

`DATABASE_URL` points to a file in an ignored folder (`.data/`), created by the first migration; each worktree has its own file. No Docker. `db:up` and `db:down` do not exist; AGENTS.md says so. On Cloudflare, SQLite means D1 with its own driver and migration command.

## ORM

- Drizzle: drizzle-kit is a devDependency of the db package with `generate` and `migrate` scripts there. Pin drizzle-orm, drizzle-kit, and the driver from one supported set; an RC generator never pairs with a stable runtime without evidence.
- Prisma: schema and generated client in the db package; `prisma generate` runs before `check`, `check-types`, `build`, `test`, and `dev`. `db:generate` is `prisma migrate dev --create-only`, `db:migrate` is `prisma migrate deploy`. Follow the Prisma docs of the frozen major for its config file, driver adapter, and env loading.

## Code

Each backend entry builds its own connection with a driver documented for its runtime and injects the db into shared code. Schema and migration config are importable without opening a connection.

Acceptance: an application query works under the selected runtime. After commit: a second worktree applies the migrations to its fresh, empty database (Postgres: another `POSTGRES_PORT`; SQLite: its own file), a rerun is a no-op, and it runs alongside the first.

Pitfall (2026-11-02): schema push is not a migration; production uses committed migrations only.
Pitfall (postgres 18 image, 2026-11-02): mount the named volume at `/var/lib/postgresql`, not `/var/lib/postgresql/data`.
Pitfall (Prisma 7.10, 2026-11-02): its docs default to the ORM 8 prerelease (v7 docs live under `/docs/orm/v7`), and its CLI loads no `.env` by itself.
Pitfall (drizzle-kit under bun's isolated linker, 2026-11-02): a root-level drizzle-kit cannot resolve the `pg` driver of `packages/db` and `migrate` exits 1 without an error message; run it from the db package.
